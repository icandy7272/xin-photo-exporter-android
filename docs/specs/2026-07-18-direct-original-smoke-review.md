# 原图直下方案 Review 与「最小成本批量下载」落地建议

> 被审查文档：[`2026-07-18-direct-original-smoke-design.md`](./2026-07-18-direct-original-smoke-design.md)
> 审查日期：2026-07-18
> 目标校准：真实目标是**批量下载自己账号的原图**，并以**最小开发成本**达成。本报告据此评审。

---

## 0. 一句话结论

**打法换对了，但当前文档把「验证一个 3 张样本的 smoke」写成了「生产级对抗安全规格」，与「最小成本批量下载」的真实目标严重错配。** 建议：保留「读 logcat 里的原图 URL 直接下载」这个核心，砍掉绝大部分安全加固，用一条 ~1 天成本的流水线先把批量下载跑通。

---

## 1. Review：为什么这个方向是对的

旧的 Mac/iPhone UI 自动化方案，所有 badcase 是同一个病——**去抓一个你不掌控的 UI，再用模拟输入驱动它**：

| 旧方案 badcase | 根因 | 新方向是否消解 |
|---|---|---|
| 照片没加载完就点下载浮层 | 渲染时序竞态 | ✅ 直接读 URL，不看渲染 |
| 向左滑动失效 / 同一张下 3 次 | 模拟手势不可靠 | ✅ 无任何模拟输入 |
| 识别 2 张只下 1 张、识别 3 张下 2 张 | 视觉计数 ≠ 实际内容 | ✅ 以 URL 计数与去重 |
| 英文纯文字点进去返回失败 | UI 状态机不可控 | ✅ 不进详情页 |
| 视频没有暴露保存按钮 | 依赖 UI 控件存在 | ✅ URL 显式，控件无关 |

新方向把战线**从「屏幕」上移到「数据源」**：App 自己把原图 CDN 地址成对打进了 logcat（`原图地址::` / `压缩地址::`）。你不再猜屏幕上有什么，而是读它亲口说出的资源标识。**这是一个更确定、更省力的立足点，方向判断成立。**

---

## 2. Review：当前设计文档的核心问题

### 2.1 最大问题——加固与目标的「层级失配」（over-engineering）

文档为一个「把 3 张**你本就拥有的** JPEG，从 CDN 下到你自己 Mac 上、放进已被 gitignore 的 `build/`」的动作，套上了：

- `renameatx_np(RENAME_EXCL)` 原子无覆盖提交、每级祖先 `openat(O_NOFOLLOW)`+`fstat` 复核；
- 描述符安全的废弃 run 清理、`--cleanup-abandoned` grammar 校验；
- SSRF 全套（禁代理、禁重定向、锁定已验证 IP、拒绝非全局地址、TLS 不可降级）；
- sentinel URL 子串扫描 stdout/stderr/临时文件/异常路径。

这些单看都对，**合起来对一个个人本地工具是过度工程**。问题不在「安全」，在**次序与配比**：在还没验证「log→下载能不能拿到可用原图、能不能覆盖全部照片」之前，就先把工作量投进了文件系统竞态加固。

### 2.2 与「批量下载」直接冲突的设计

| 文档条款 | 与批量下载的冲突 |
|---|---|
| 恰好 3 个候选、每个最多 1 次 GET、全程 ≤3 次 | 目标是**全量**，不是 3 张 |
| 任一失败 / 内容重复 → 整个 run 失败、不替补 | 批量场景里必然偶发失败，一票否决 = 永远跑不完 |
| 完全拒绝 `%` 百分号编码 | 文件名带空格/Unicode 的图会被**静默漏掉** |
| 最多读 8 MiB / 50k 行、超限 fail closed | 重度账号会直接拒绝运行（见 §4 环形缓冲）|

### 2.3 值得保留、精简时别误伤的优点

- **技术声明诚实**：不声称「证明是上传源文件」「证明账号所有权」，把画质/归属判断交给用户人工确认。保留。
- **隐私原则**（URL/照片/EXIF 不进 Git、日志、报告）正确且**低成本可满足**（见 §5）。
- **文件完整性校验思路**（是不是合法 JPEG）值得保留一个最小版。

## 3. 回到真实目标：最小成本批量下载

**目标重述**：把当前登录账号在 App 里能加载出来的原图，尽量全地、去重地、可续跑地下载到本机一个目录。仅此而已。

### 3.1 最小可行流水线（4 步）

```text
①  边滚边录 logcat  →  ②  抽取 + 去重 URL  →  ③  循环下载(跳过已存在)  →  ④  校验计数
```

一个 shell 版本就能跑通（示意，非最终代码）：

```bash
# ① 边滚边录：解决环形缓冲——流式录制，同时在 MuMu 里从头滚到尾让 App 打出全部 URL
adb logcat -c                       # 清一次拿干净起点（个人工具可接受）
adb logcat > feed.log &             # 后台流式录制
#   ...此时手动或用 UI Automator 把整个相册从头滚到底...
kill %1

# ② 抽取 + 去重
grep -oE '原图地址::https://cdn-mctchildfoliocn\.childfolio\.net/\S+\.jpeg' feed.log \
  | sed 's/^原图地址:://' | sort -u > urls.txt

# ③ 下载（跳过已下的，天然可续跑）
mkdir -p build/originals
while read -r url; do
  f="build/originals/$(printf '%s' "$url" | shasum -a256 | cut -c1-16).jpeg"
  [ -f "$f" ] && continue
  curl -fsS --max-time 120 "$url" -o "$f.part" && mv "$f.part" "$f" || echo "FAIL $url" >> fails.txt
done < urls.txt

# ④ 校验
echo "downloaded: $(ls build/originals | wc -l)  |  failed: $(wc -l < fails.txt 2>/dev/null || echo 0)"
```

> 若在意「URL 出现在进程列表」这一条隐私顾虑，把 ③ 换成一个 ~30 行的 Python（`requests` 流式下载 + skip-if-exists）即可，成本几乎一样、更稳，也顺带能加最小 JPEG 校验（前两字节 `FF D8`、大小 >1KB）。这是我推荐的中间档。

**整体工作量：约 1 天**（含调试滚动触发日志、跑一次全量、抽查画质），而不是当前 spec 的数天加固。

### 3.2 保留 / 砍掉 对照表（给「别太大了」的核心答案）

| 当前 spec 机制 | 对批量下载 | 建议 |
|---|---|---|
| 从 logcat 解析原图 URL | 核心 | ✅ **保留** |
| host 固定为已知 CDN、`.jpeg` 结尾 | 防误抓其它 URL | ✅ **保留**（一个正则即可）|
| 文件完整性最小校验（是 JPEG、大小>0、按 URL 去重）| 保证下到完整图 | ✅ **保留最小版** |
| 账号归属确认 | 伦理/合规边界 | ✅ **保留**，但口头/一句话确认即可，不需 `--attest` 仪式 |
| 边滚边流式录 logcat | 覆盖全部照片 | ✅ **新增**（比 spec 的一次性读+fail-closed 更能对抗环形缓冲）|
| 恰好 3 个 / 一失败全灭 / 不替补 | 目标是全量 | ❌ **砍**（改为：失败记 `fails.txt`，重跑续传）|
| 每候选 1 次 GET、全程 ≤3 次预算 | 批量本就要下很多 | ❌ **砍** |
| 完全拒绝 `%` 编码 | 会静默漏图 | ❌ **砍**（正常 URL 解码）|
| SSRF 全套（禁代理/锁 IP/拒非全局地址）| 防打内网 | ⚠️ **降级**：host 锁定已知 CDN 就够 |
| openat/O_NOFOLLOW/renameatx_np/fstat 复核 | 防路径替换竞态 | ❌ **砍**（固定输出目录 + `.part`→rename 足够）|
| 描述符安全废弃 run 清理 + `--cleanup-abandoned` | 崩溃残留 | ❌ **砍**（skip-if-exists，重跑即清）|
| sentinel 子串扫描 stdout/临时文件 | 防 URL 泄露 | ❌ **砍**（`.gitignore` + 不 commit 日志即可，见 §5）|
| 零网络 dry-run + 请求计数=0 断言 | 可测试性 | ⚠️ **可选**：留一个 `--dry-run` 只打印「将下载 N 张」就够 |

## 4. 不能省的几个真实约束

这些不是安全加固，而是**决定「批量下载」能不能真正跑全**的点，务必正视：

- 🔴 **logcat 是环形缓冲，会被截断。** 这是全量覆盖的头号约束。**一次性 `adb logcat -d` 只能拿到缓冲里还剩的部分**；账号历史久或设备忙时，早期 URL 早被挤走。→ 对策就是 §3.1 的「**边滚边流式录制**」：一边滚动触发 App 加载、一边把日志实时写进文件，而不是滚完再回头一次性 dump。
- 🟠 **滚动没被消灭，只是降级了。** 直下解决的是「下载」；「让 App 把 URL 打出来」仍然需要把相册滚一遍。但这已经从「滚动+点击+滑动+保存」退化成「只滚动」，可靠性收益巨大。先手动滚验证可行，再决定要不要上 UI Automator 自动滚。
- 🟠 **整套方案寄生在 App「明文打 URL 到 logcat」这个行为上。** 这本质是对方的一个隐私实现细节，任何版本更新都可能移除。→ 低成本对冲：加一句「本次抽到 0 个 URL 就报警提示日志格式可能已变」，别让它静默返回空。
- 🟡 **「原图地址」未必是上传源文件。** 可能是服务端重编码。保持 spec 的诚实声明，画质靠用户对已知照片人工抽查确认。

---

## 5. 隐私原则如何低成本满足

README 的隐私原则（URL/照片/EXIF 不进 Git、普通日志、报告）是对的，而且**几乎零成本**就能满足，不需要那套描述符安全机制：

- 现有 `.gitignore` 已覆盖 `build/`、`*.jpeg`、`*.part`、`report.json` → 产物天然不入库；
- 把 `feed.log`、`urls.txt`、`fails.txt` 也加进 `.gitignore`；
- 唯一纪律：**不要把含 URL 的日志/命令输出粘进 commit、issue 或对话记录**。

这三条就把 spec 里「sentinel 扫描 + 闭集错误枚举 + 禁用一切调试日志」想达到的效果，用可接受的方式覆盖了。

---

## 6. 建议的推进顺序

1. **薄验证（半天）**：手动滚一屏 → `adb logcat -d | grep 原图地址` → 挑 3 个 URL 用 `curl` 下下来 → 打开确认画质。**这一步为「是」之前，别写任何工具代码。**
2. **最小批量（半天~1 天）**：把 §3.1 流水线跑通，边滚边录一次全量，得到「下载 N 张 / 失败 M 张」，抽查画质与去重。
3. **按需增强（可选）**：UI Automator 自动滚、失败重试、最小 JPEG 校验、`--dry-run`。
4. **生产化再谈加固**：真要做成给别人用的工具时，再从当前 spec 里把 TOCTOU/SSRF/信号处理**按需**捡回来——那时它们是资产，现在只是过早负重。

---

## 7. 需保留的前置确认（精简版）

执行前用户口头确认即可，不需要 flag 仪式：

1. 当前 MuMu 实例与账号是本人所有或已获授权导出；
2. 本次会话未切换账号；
3. 明白样本 JPEG 可能自带敏感 EXIF，仅本机短期查看。

## 附：一句话总结

> 方向对了（从抓 UI 变成读数据源，旧 badcase 基本一次性消解）。现在唯一要做的是**克制**：先用一条 ~1 天的流水线证明「批量下载」能跑通，把那套生产级加固留到真正要产品化时再说。
